# 全栈挑战要求检查：问题说明

本文整理对照《【睿迄科技】全栈开发3天挑战》检查仓库时发现的四项问题，包含触发条件、原因、影响和修复建议。不包含交付材料、README 信息修正、支付重放说明及仓库访问权限问题。

检查基于提交 `ae075a68db58875325b899787fe56a9b110aa94a`。前三项是已复现的代码缺陷，第四项是自动化测试覆盖缺口，并非已证实的页面故障。

## 检查背景

- 当前网页的公制填写、刷新恢复、结果展示和模拟支付解锁主流程已经手动验证通过。
- 本地 Lint、类型检查、生产构建和 Prisma schema 校验均通过。
- 本地覆盖率测试共 249 个用例，全部通过；行覆盖率为 89.65%，分支覆盖率为 86%。当前提交的 GitHub CI 同样通过。
- 测试通过说明现有用例验证的行为成立，不代表所有输入组合和调用路径都已覆盖。
- PDF 没有要求必须支持英制，也没有要求必须使用 Playwright。英制问题属于项目已经提供、但没有完整实现的能力；缺少浏览器自动化也不能单独作为不达标的依据。

## 1. 英制数据保存成功，但提交计算失败

### 预期行为

后端允许用户提交英制或公制身体数据。英制输入应在入口处转换成公制后保存，随后能够正常恢复、提交计算并生成结果。

### 触发条件与复现步骤

1. 创建一个新测评会话。
2. 填写性别、目标、运动频率等必填步骤。
3. 使用以下英制格式保存身体数据：

```json
{
  "unitSystem": "IMPERIAL",
  "age": 28,
  "heightIn": 65,
  "weightLb": 155,
  "goalWeightLb": 135
}
```

4. 调用 `POST /api/v1/sessions/:id/submit` 提交测评。

线上实际结果：身体数据保存成功，但最终提交返回 `422 VALIDATION_FAILED`。错误指出缺少 `heightIn`、`weightLb`、`goalWeightLb`，同时不接受 `heightCm`、`weightKg`、`goalWeightKg`。

### 原因

保存时，`bodyMetricsSchema` 会把英制数值转换成公制。数据库保存的值类似：

```json
{
  "unitSystem": "IMPERIAL",
  "age": 28,
  "heightCm": 165.1,
  "weightKg": 70.3,
  "goalWeightKg": 61.2
}
```

保留原始单位偏好、统一保存公制数值，本身可以是合理设计。问题在于提交阶段的 `assembleAssessmentInput()` 又使用原始输入校验规则解析这份数据库记录。

该规则根据 `unitSystem` 选择字段格式。看到 `IMPERIAL`，就要求英制字段；但这些字段已经在保存阶段被转换掉了。因此，已经规范化的数据无法再次通过面向原始输入的校验。

相关代码：

- [src/lib/quiz/steps.ts](../src/lib/quiz/steps.ts)：英制输入校验与公制转换。
- [src/lib/quiz/service.ts](../src/lib/quiz/service.ts)：`saveAnswer()` 保存转换结果，`assembleAssessmentInput()` 再次解析身体数据。

### 影响范围

通过 API 使用英制输入的客户端会在提交阶段被阻断，无法生成结果。当前网页固定发送 `METRIC`，没有英制切换入口，所以现有网页主流程通常不会触发该问题。

### 为什么现有测试没有发现

现有测试验证了英制输入能够转换并保存，没有继续验证同一份已保存答案能够成功提交并生成结果。单独看保存操作是正确的，两个阶段连接起来才出现格式不匹配。

### 修复建议

将原始请求和数据库记录的校验职责分开：

- 原始输入 schema 接受英制或公制，并统一转换数值。
- 规范化数据 schema 校验数据库中的公制字段，不再执行原始输入转换。
- 如果需要保留用户的单位偏好，应明确它是显示偏好，避免让它同时决定数据库字段的量纲和格式。

### 建议补充的回归验证

验证完整链路：英制输入保存成功 → 读取恢复数据 → 提交成功 → 结果持久化成功。检查转换后的输入快照正确，且没有重复换算单位。

## 2. 已作废会话仍允许修改答案

### 预期行为

按当前项目对状态的定义，一次测评具有以下状态：

| 状态 | 含义 | 是否允许修改答案 |
| --- | --- | --- |
| `IN_PROGRESS` | 正在填写 | 允许 |
| `COMPLETED` | 已完成并生成结果 | 不允许 |
| `ABANDONED` | 用户已放弃，例如选择重新开始 | 不允许 |

作废后可以保留历史读取能力，但不应继续修改答案和填写进度。

### 触发条件与复现步骤

1. 创建会话并保存至少一个答案。
2. 调用 `POST /api/v1/sessions/:id/abandon`，确认返回 `ABANDONED`。
3. 保留该会话对应的有效 token，在会话尚未过期时，再次 PATCH 旧会话的答案。
4. 写入请求不带版本号，或携带当前有效的版本号。

线上已复现：作废接口返回 `200` 和 `ABANDONED`，随后修改性别答案仍返回 `200`，答案 revision 递增。

### 原因

`assertWritable()` 当前只检查：

```text
如果状态是 COMPLETED，拒绝。
如果会话已过期，拒绝。
其他情况放行。
```

其中没有对 `ABANDONED` 的拦截。后续保存事务也没有把“状态必须为 IN_PROGRESS”作为更新条件。

相关代码：

- [src/lib/auth/authenticate.ts](../src/lib/auth/authenticate.ts)：`assertWritable()`。
- [src/lib/quiz/service.ts](../src/lib/quiz/service.ts)：`saveAnswer()` 的事务更新条件。
- [作废接口](../src/app/api/v1/sessions/[id]/abandon/route.ts)：把旧会话标记为 `ABANDONED`。

### 什么时候会遇到

例如，自定义客户端继续向旧会话发送请求，或用户在多个标签页操作同一会话。一个标签页选择重新开始，另一个仍保留旧会话的凭证。

需要区分状态检查和版本检查：旧标签页携带旧版本号时，可能先被乐观锁拒绝。但不带版本号，或读取最新版本后再提交，仍能写入。因此乐观锁没有替代作废状态检查。

### 影响范围

该问题本身不会绕过身份鉴权，调用者仍需要旧会话对应的 token。已经证明的是状态一致性缺陷，而不是越权访问。

结果是数据库里的记录仍标记为“已放弃”，答案和当前步骤却继续变化，使后续状态判断、流失分析和清理逻辑面对矛盾的数据。

### 为什么现有测试没有发现

现有作废测试覆盖了状态变化、重复作废、已完成会话拒绝作废、越权作废以及作废后读取，但没有验证“作废后写入必须失败”。

### 修复建议

明确只有 `IN_PROGRESS` 状态可以修改答案；同时在数据库事务的更新条件中约束状态，避免请求通过检查后，会话又被另一个请求作废或完成。

### 建议补充的回归验证

- 作废后 PATCH 被拒绝，答案、revision、version 和作答流水均不改变。
- 作废后提交计算被拒绝，不能重新变成已完成状态。
- 作废后仍能读取历史答案，符合现有读取约定。
- 保存与作废并发发生时，不会出现“作废后又成功修改”的状态矛盾。

## 3. 增重分支遗漏摄入下限检查

### 预期行为

项目定义了按性别区分的摄入下限，并声明建议摄入量不低于该下限。减重、维持和增重分支都应遵守同一约束，或者明确拒绝不适用的输入组合。

这里检查的是代码与项目自身规则是否一致，并不将这些常量视为适用于所有人的医学结论。

### 触发条件与复现输入

当目标体重高于当前体重，且计算出的每日总消耗足够低时，可能触发该问题。已使用以下输入在本地算法调用中复现：

```json
{
  "gender": "FEMALE",
  "age": 100,
  "heightCm": 90,
  "weightKg": 30,
  "goalWeightKg": 35,
  "goal": "GAIN_MUSCLE",
  "activityLevel": "SEDENTARY"
}
```

这组输入处于当前校验允许的字段范围内，目标体重偏离比例也未超过限制。

按照仓库自身公式，结果为：

| 计算项 | 结果 |
| --- | --- |
| 基础代谢 | 202 |
| 每日总消耗 | 242 |
| 增重增加的热量 | 550 |
| 最终建议摄入 | 792 |
| 项目设置的对应下限 | 1200 |

最终的 `792` 低于项目设置的 `1200`。

### 原因

三个分支对下限的处理不一致：

| 分支 | 当前行为 |
| --- | --- |
| 减重 | 总消耗减去缺口，再检查下限 |
| 维持 | 总消耗与下限取较大值 |
| 增重 | 总消耗加上盈余，没有检查下限 |

增重分支相当于假设“加上盈余以后，一定高于下限”。当原始总消耗很低时，这一假设不成立。

相关代码：

- [src/lib/health/algorithm.ts](../src/lib/health/algorithm.ts)：`direction === 1` 的增重分支。
- [src/lib/health/constants.ts](../src/lib/health/constants.ts)：`CALORIE_FLOOR` 和输入范围。

### 影响范围

普通输入未必会触发，低体重、低身高、高年龄等组合更容易产生较低的计算值。这个例子虽然极端，但系统当前选择接受它，就应返回符合自身约束的结果，或者明确表示无法提供适用方案。

### 为什么现有测试没有发现

[算法测试](../tests/unit/health/algorithm.test.ts) 中有一条名为“建议摄入在任何输入下都不低于对应性别的下限”的用例，但实际只遍历性别，目标始终为 `LOSE_WEIGHT`，体重方向也始终为减重。

它能验证减重分支，不能证明增重分支也遵守下限。测试名称描述的范围大于实际覆盖范围。

### 修复建议

统一检查各分支的摄入下限，并明确极端输入下的处理策略。不能只将最终摄入量改成较大值，还应保证调整后的摄入量、有效体重变化速率和预测日期一致。如果既定约束无法同时满足，应明确返回限制或无法预测的状态，而不是静默产出自相矛盾的方案。

### 建议补充的回归验证

覆盖性别、体重变化方向和低总消耗输入的组合，至少验证：

- 增重输入不会返回低于项目规定下限的摄入量。
- 调整摄入量后，变化速率和预测日期遵守项目选定的计算规则。
- 极端但可接受的输入有明确结果或限制说明。

## 4. 自动化测试与真实浏览器支付路径之间存在缺口

### 当前已经验证了什么

现有支付测试直接调用 route handler，并连接真实测试数据库，验证：

```text
创建并完成测评
→ 读取免费结果
→ 直接调用 /pay 对应的处理函数
→ 数据库订阅状态改变
→ 读取结果
→ 确认从 FREE 变成 PREMIUM
```

这能够验证服务端签名处理、支付业务逻辑、数据库状态及差异化返回，不能称为“完全没有端到端验证”。

相关测试：[tests/integration/access-and-payment.test.ts](../tests/integration/access-and-payment.test.ts)。

### 用户实际走的路径

当前网页点击“立即解锁”时，走的是：

```text
点击按钮
→ 浏览器请求 /api/v1/checkout
→ /checkout 校验参数与会话身份
→ 调用共享的 processPayment()
→ 数据库订阅状态改变
→ 前端重新请求结果
→ 页面显示完整方案
```

`/checkout` 直接复用支付业务函数，没有实际发送 HTTP 请求到 `/pay`。这种模拟支付实现可以成立，但测试 `/pay` 不会自动覆盖 `/checkout` 的路由处理和前端交互。

相关代码：

- [src/app/api/v1/checkout/route.ts](../src/app/api/v1/checkout/route.ts)。
- [src/lib/client/api-client.ts](../src/lib/client/api-client.ts)：浏览器的 checkout 请求。
- [结果页面](../src/app/result/[sessionId]/page.tsx)：支付动作及支付后的结果刷新。

### 缺少的自动化保证

当前测试没有经过真实 HTTP 服务或浏览器操作；覆盖率报告中 `/checkout` 为 0%。因此，现有套件不能直接验证按钮事件、浏览器凭证传递、该路由的请求处理以及解锁后的页面更新是否配合正确。

### 什么时候会暴露

例如，未来一次修改可能造成以下情况：

- 前端请求地址或字段名发生错误。
- checkout 请求漏传 token。
- 支付成功后没有重新请求结果，页面仍显示付费墙。
- 进度恢复或路由跳转异常，使用户无法到达结果页。
- 部署环境的 HTTP 中间层行为与直接调用处理函数不同。

这些情况下，底层支付业务仍可能正确，原有测试也可能继续通过，但用户无法完成完整流程。

### 是否意味着当前页面已经有故障

不意味着。线上填写、刷新恢复、模拟支付以及完整方案展示已经手动验证通过。这一项指出的是缺少持续的自动化保证，不是已复现的支付页面故障。

PDF 没要求必须使用 Playwright。应按验证范围评价测试，而不是按是否采用某个框架评价：目前已经覆盖服务端支付闭环，但可以进一步补齐真实 HTTP 或浏览器层的验证。

### 修复与补充测试建议

补充 `/checkout` 的接口测试，覆盖有效调用、缺少凭证、越权访问和非法套餐等路径。

再增加至少一条完整浏览器自动化流程：

```text
新用户开始测评
→ 保存部分答案
→ 刷新页面并确认恢复
→ 完成测评
→ 验证免费结果与受保护数据缺失
→ 点击模拟支付
→ 验证完整方案显示
→ 再刷新，确认权益与结果仍然保留
```

浏览器测试用于补充用户路径的验证，现有服务端单元测试和集成测试仍应保留，继续承担边界、异常和数据库一致性验证。

## 建议处理顺序

先修复前三项已复现的代码缺陷，并为每项补上能够在修复前失败、修复后通过的回归测试。随后补齐 `/checkout` 测试及浏览器完整流程自动化，减少后续修改破坏已跑通流程的风险。

本文仅记录检查结果与建议，没有实施上述业务代码修复。
